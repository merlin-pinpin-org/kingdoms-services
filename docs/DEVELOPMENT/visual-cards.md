# Visual cards — one image instead of heavy embeds/views

Some messages and forum posts are essentially **one picture plus a lot
of facts**. Rendering them as a single image — generated by the
[visual-generator](https://github.com/merlin-pinpin-org/visual-generator)
library from JSON data — replaces multi-block LayoutViews and long
embeds with a lighter, brand-stable post.

This guide is for **agents and developers**: when to reach for a
visual card, how to build one, and how to send it.

## When to use what (the decision table)

| Situation | Use |
|---|---|
| Short status, confirmation, error, ladder line | **Embed** (ADR-0009) |
| Anything interactive (buttons, selects, modals) | **Components V2** (`ui/factory.py`) |
| Content that must re-render per audience without a new image | **Components V2** (`ui/delivery.py`) |
| Read-only content, one entity, structured facts, ≤ 4 images | **Visual card** (`visual_cards.py`) |

The rule of thumb: **if the post is "a picture plus facts" and nobody
clicks anything on it, it is a visual card.** The card is an image
attachment; the post's text content stays as the searchable, screen-
reader-friendly fallback. The library OCR-guarantees that the image
says the same thing as the text.

## The three card builders

`src/kingdoms/discord/visual_cards.py` maps platform entities onto
the library templates (schemas, CLIs and pitfalls: the library's
agent skill, `.agents/skills/visual-generator/SKILL.md`):

- `faction_card(faction, content, tags, facts)` → library
  `info_card`: one image (the civ's emblem/illustration) + tag chips +
  label/value columns (strengths, unique unit…).
  `content` is the `(name, summary, source, image)` tuple from
  `entity_post_content`.
- `map_card(map_entry, images, tags, facts, description)` → library
  `media_card`: image strip (up to 4), tags, facts line, and a
  **synthesized** description — never dump the raw description, the
  card wraps and *visibly clips* it; condense first.
- `player_card(display_name, avatar_url, games, profile_ids)` →
  library `info_card`: the player's avatar, pseudo, the games they
  play, their profile ids.

## How to send one

```python
import os

import discord

from kingdoms.discord.visual_cards import player_card

card = player_card(
    display_name=user.display_name,
    avatar_url=user.display_avatar.url if user.display_avatar else None,
    games=[["aoe2", profile.in_game_name or "actif"]],
    profile_ids=[["aoe2", profile.game_id]],
)
await channel.send(
    content=card.caption,
    file=discord.File(card.path, filename=os.path.basename(card.path)),
)
```

For the entity forums (factions, maps), the `EntityForumSpec` now
accepts an optional `build_attachment(entity, guild_id)` that
returns a `discord.File`; the forum engine attaches it to the
starter message on creation, and `create_map_post(..., attachment=)`
carries it. The factions forum already does this
(`factions_forum.build_faction_card`); the maps forum can follow the
same pattern.

## How agents learn this

When a task says "post/display/present entity X in a forum" and X is
read-only with facts and images:

1. Do **not** stack TextDisplay/MediaGallery blocks — check the
   decision table above.
2. Build the JSON through `visual_cards.py` (never call the library
   with a hand-made schema; the builders keep slugs, palettes and
   footers consistent).
3. Render + validate: the library is fail-closed; in sandboxes
   without tesseract, OCR the image with the available engine before
   delivery (see the library skill's validation contract).
4. Send the card as an attachment with the text content as fallback;
   never link a sandbox path — the file travels with the message.
5. If the card fails to render, the post falls back to its
   LayoutView: wrap builder calls in `try/except` and log at debug,
   as `build_faction_card` does.
